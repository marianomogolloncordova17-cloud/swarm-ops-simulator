🌐 Enjambre Público (Petals WAN) COLUMNA ACTIVA

  • Latencia media / salto: ~60 ms/salto → ~2–4 tok/s (rango real del enjambre público).
  • Privacidad / Compliance: ❌ Nula — las activaciones de tus prompts viajan por GPUs de desconocidos.
  • Tiempo 100 pasos LoRA (360 MB @ 50 Mbps): ~60 s de cuello de botella de red.
  • Costo mensual: $0 USD (pero inviable para datos privados de clientes).

🏢 Enjambre Oficina LAN (Exo / Petals Privado) COLUMNA ACTIVA

  • Latencia media / salto: ~20 ms/salto → ~14–22 tok/s en decode (dominado por cómputo, no por red — Exo real).
  • Privacidad / Compliance: ✅ 100% Soberana — los paquetes nunca salen del router de la oficina.
  • Tiempo 100 pasos LoRA (360 MB @ 1 Gbps LAN): ~3 s de sobrecarga de red (×20 más rápido que WAN).
  • Costo mensual: $0 USD CapEx extra — reutiliza las 6 laptops/Macs/PCs que ya tiene el equipo en horario valle.

☁️ Clúster Cloud Dedicado (AWS / RunPod 8×GPU)

  • Latencia: Muy baja (NVLink interno), máxima velocidad.
  • Privacidad: ⚠️ Terceros — requiere contratos DPA / salida de datos a la nube.
  • Costo mensual: $1,800 – $4,500 USD/mes (instancias multi-GPU dedicadas para modelos grandes).
Nota técnica: Los valores de latencia y throughput (14–22 tok/s en LAN) reflejan estimaciones físicas de red y cómputo. La animación de los paquetes se escala visualmente (suelo de 14 ms/salto en LAN) para que el flujo sea observable por el ojo humano.

Mapa 2026 del entrenamiento/inferencia descentralizada lo que faltaba en la tabla original

Petals 2026: latente

  • Pipeline P2P global: el modelo se parte en bloques entre voluntarios; la KV cache vive en cada peer.
  • Estado real: sin commits desde ago 2024, clavado a transformers 4.43.1; sin soporte Windows nativo.
  • Hoy sirve para: aprender — y brilla en red privada (Plan B), no en producción.

Exo 2026: activo

  • Enjambre en tu LAN/WiFi: descubre solos portátiles, PCs, Macs e incluso teléfonos.
  • Anillo gRPC: reparte capas según la RAM/VRAM real de cada equipo.
  • El camino rápido: clona exo-explore/exo, ejecuta exo en cada dispositivo y listo.

DiLoCo / OverlapSPARTA 2026: investigación

  • Low-communication training: N pasos locales → una sola sincronización (promediado o subconjunto de parámetros).
  • Ataca el muro real: el ancho de banda, no el cómputo.
  • Es la línea que Petals no resolvió: su fine-tune sigue dependiendo del pipeline completo.

# requiere Python 3.8–3.10 (no 3.12+) · en Windows: WSL2 o Docker
pip install git+https://github.com/bigscience-workshop/petals

# ⚠️ usa un modelo que aparezca ACTIVO en https://health.petals.dev
import torch
from transformers import AutoTokenizer
from petals import AutoDistributedModelForCausalLM

MODEL = "meta-llama/Meta-Llama-3.1-8B-Instruct"  # gated: requiere HF token
tokenizer = AutoTokenizer.from_pretrained(MODEL)
model = AutoDistributedModelForCausalLM.from_pretrained(MODEL)

inputs = tokenizer("¿Cuál es el futuro de la IA?", return_tensors="pt").to(model.device)
out = model.generate(**inputs, max_new_tokens=30, do_sample=True, temperature=0.6)
print(tokenizer.decode(out[0]))

Exo reparte el modelo en anillo por gRPC según la memoria de cada equipo. Para entrenamiento distribuido real sobre redes lentas, el estado del arte 2026 son DiLoCo (Distributed Low-Communication: cada nodo entrena k pasos y promedia pseudo-gradientes) y OverlapSPARTA (intercambia solo un subconjunto de parámetros solapado con el cómputo).

🔬 Nota para la auditoría — qué modela de verdad este simulador

Simulado con mecánicas reales:
  • Latencia por salto: RTT propio por peer (26–48 ms) + cómputo por bloque (4 ms decode / 15 ms prefill).
  • WAN vs LAN (física conmutable): en WAN la latencia la domina el RTT de red (26–48 ms/salto + 70 ms de retorno de logits); en la oficina LAN gigabit cae a 2 ms/salto + 3 ms de retorno y el coste por token queda dominado por el cómputo de los bloques en cada GPU — el interruptor usa effRtt/effRet y JAMÁS muta p.rtt, así el regreso a WAN restaura los RTT reales sin copias guardadas.
  • Saltos reales: la latencia media se calcula sobre saltos reales (tramos + retorno al cliente) — «Saltos/token» cuenta exactamente los mismos saltos que anima el paquete.
  • Prefill vs decode: el primer token es prefill (~3.5× más caro); luego la KV cache acelera cada token.
  • KV cache por bloque en el peer anfitrión: si el peer cae, la KV se pierde → re-prefill parcial visible en naranja.
  • Churn & DHT: bloque sin anfitrión → réplica (instantáneo) o nuevo peer que descarga pesos (~0.5 GB/bloque) respetando la VRAM real de cada peer — sin límite mágico de bloques.
  • VRAM heterogénea: cada peer tiene su techo según su GPU simulada (Alpha 8 GB → 14 bloques; Epsilon 4 GB → 6, nace lleno; Zeta 3 GB → 4, nace lleno).
  • Cliente ligero real: embeddings + B0–B1 se computan EN TU MÁQUINA (pulso local, cero saltos de red, KV client-side); el enjambre solo aloja B2–B31.
  • Loss en el cliente (rigor canónico): el forward termina en Zeta → las activaciones ocultas vuelven al cliente → lm_head + cross-entropy EN TU MÁQUINA → d(hidden) inicia el backward hacia Zeta y desciende el pipeline.
  • Contadores de comunicación en entrenamiento: 3.6 MB/paso (activaciones+gradientes; 1.8 MB con cuantización INT8/NF4) vs 120 MB/100 pasos (DiLoCo). El adapter LoRA (12 MB) se guarda en el cliente — nunca se sube al enjambre.
Lo que NO modela (honestidad ante todo):
  • Red real ni DHT real (libp2p/hivemind): todo es local y determinista.
  • Tokens de un modelo real: la respuesta es plantilla tokenizada estilo sentencepiece (▁).
  • Ancho de banda variable ni topología de anillo de Exo.
  • La cuantización INT8/NF4 solo divide el tráfico simulado: no modela su coste de cómputo ni el error numérico.
  • Seguridad: sin poisoning, sin consenso ni pruebas ZK.
